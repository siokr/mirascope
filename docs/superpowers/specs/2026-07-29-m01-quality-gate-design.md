# M01-016 自动化质量门槛设计

## 目标

把 `docs/quality-strategy.md` 中适合自动执行的合并门槛固化为 GitHub Actions，让每次推送和 Pull Request 都能得到可追溯的当次结果。

## 范围

自动门槛分成两个独立作业：

1. `quality`：在 Ubuntu 上执行依赖获取、格式检查、静态分析和全量测试；
2. `windows-build`：在 Windows 上生成 release 构建，验证目标平台产物可生成。

两个作业互不掩盖结果。Windows 构建失败时，格式、分析和测试结果仍然可见；自动构建成功也不替代真实文件选择、窗口交互和进度恢复的人工验收。

## 工具链

- Flutter 固定为项目当前使用的 `3.44.8`，避免 `stable` 漂移造成不可复现；
- Dart 由 Flutter SDK 提供；
- 依赖使用已提交的 `pubspec.lock`；
- GitHub Actions 权限限制为只读仓库内容；
- 使用并发取消，新的同分支运行会取消旧运行，减少无效等待。

## 格式范围

格式检查覆盖项目维护的 `lib` 和 `test`。生成目录、平台模板与外部工具目录不参与 Dart 格式门槛，避免工作区缓存影响结果。

## 触发与证据

- 推送到任意分支时运行；
- 针对 `main` 的 Pull Request 运行；
- 支持手工触发；
- GitHub Actions 页面保存每个步骤的日志和结论；
- M01-016 的任务状态只依据本次实际结果更新，不把工作流文件存在等同于远程 CI 已通过。

## 非目标

- 不发布安装包；
- 不自动推送或合并；
- 不替代 Windows 实机人工验收；
- 不在本阶段建立性能基线；
- 不上传可能包含本地数据的测试产物。
