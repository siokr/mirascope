# mirascope 文档体系重构设计

## 1. 背景

`mirascope` 是个人长期维护项目，同时承担三个用途：

- 作为作者自己使用的本地阅读与媒体管理工具；
- 作为求职时能够实际演示、解释和复盘的代表项目；
- 作为公开在 GitHub 上供交流学习的工程项目。

当前文档已经说明产品愿景、主要模块和技术方向，但仍存在 MVP 边界冲突、优先级不一致、验收条件偏主观、时间表缺少估算依据等问题。现有文档可以支持 Flutter 工程初始化，尚不足以稳定指导完整 MVP 开发。

本次重构只修改项目文档，不修改业务代码。

## 2. 目标

本次文档重构需要达到以下结果：

1. 建立唯一、明确的版本范围，避免下载、番剧、同步等能力在不同文档中出现冲突。
2. 将首个展示版本聚焦到真实可用的本地阅读体验，而不是技术栈数量。
3. 给每个阶段配置可验证的进入条件、交付物和验收标准。
4. 把数据模型、小说导入、漫画阅读和同步等高风险能力拆成独立设计文档。
5. 说明文档之间的权威关系，降低重复内容和后续漂移。
6. 让 GitHub 访问者能够快速理解项目状态、运行方式、架构选择和后续路线。

## 3. 核心产品策略

采用“阅读体验优先、工程能力渐进展示”的路线。

### 3.1 版本路线

#### MVP 0.1：Windows 本地 TXT 阅读闭环

范围：

- Flutter 工程骨架；
- Windows 主平台；
- 本地媒体库；
- TXT 导入；
- 章节识别；
- 基础阅读器；
- 阅读进度持久化；
- 基础主题、日志、错误处理与测试。

核心演示路径：

`导入 TXT -> 加入媒体库 -> 打开阅读 -> 切换章节 -> 退出 -> 恢复进度`

#### MVP 0.2：可公开展示的小说阅读器

范围：

- Android 主流程适配；
- EPUB 导入；
- 阅读器排版与交互完善；
- 书签和阅读设置；
- 性能、异常文件和数据恢复测试；
- Windows 与 Android 演示包；
- GitHub 安装、截图、已知问题和版本说明。

#### Version 0.3：本地漫画阅读

范围：

- 本地漫画目录或压缩包导入；
- 漫画详情与章节组织；
- 图片预加载和缓存；
- 纵向滚动与横向翻页；
- 阅读进度恢复。

在线漫画源不进入 0.3，避免内容来源、网络协议和合规问题阻塞本地漫画阅读。

#### Version 0.4：账号与同步

范围：

- Go API；
- PostgreSQL；
- 登录与设备标识；
- 收藏、阅读进度、书签和设置同步；
- 增量同步、幂等、删除传播、冲突处理和失败恢复。

#### 后续版本

- 在线内容源；
- 下载系统；
- 番剧播放；
- Rust 性能模块；
- 其他桌面和移动平台。

Rust 不是预设的早期必需技术。只有性能基准证明 Dart 实现无法满足已经定义的指标时，才建立 Rust 模块。

### 3.2 平台策略

- 0.1 主平台：Windows。
- 0.2 主平台：Windows、Android。
- macOS、iOS、Linux、Web 保留为长期兼容目标，不进入早期版本承诺。
- 每增加一个正式支持平台，都必须补齐构建、运行、测试和发布检查。

## 4. 文档信息架构

### 4.1 权威文档

- `README.md`：项目入口、当前状态、快速开始和文档导航。
- `plan.md`：产品范围、版本路线、成功指标、风险和长期方向。
- `docs/mvp-task-list.md`：当前版本的可执行任务、依赖和验收。
- `docs/tech-architecture.md`：系统边界、演进策略和关键架构决策。
- `docs/project-structure.md`：仓库与客户端代码组织规则。
- `docs/dev-setup.md`：可复现开发环境，不保存无日期的临时机器状态。
- `docs/README.md`：文档索引、权威关系和维护规则。

### 4.2 新增设计文档

- `docs/data-model.md`：本地数据模型、关系、索引、迁移、生命周期和删除语义。
- `docs/novel-reader-spec.md`：TXT/EPUB 导入、章节识别、阅读状态、错误与性能标准。
- `docs/manga-reader-spec.md`：本地漫画格式、章节模型、缓存、阅读模式和验收。
- `docs/sync-protocol.md`：同步版本、游标、幂等、删除、冲突、重试和恢复。
- `docs/quality-strategy.md`：测试层级、平台矩阵、性能指标和质量门槛。
- `docs/release-checklist.md`：演示包和 GitHub Release 的发布检查。
- `docs/decisions/README.md`：架构决策记录规则。

### 4.3 单一信息源规则

- 版本范围只在 `plan.md` 定义，其他文档引用版本编号，不重新解释范围。
- 当前任务和状态只在 `docs/mvp-task-list.md` 维护。
- 技术选型结论记录在架构文档或 ADR；任务清单只引用结论。
- 数据字段只在 `docs/data-model.md` 定义。
- 同步规则只在 `docs/sync-protocol.md` 定义。
- 环境实测信息必须带检测日期；容易变化的版本信息优先由命令或配置文件提供。

## 5. 任务设计

`docs/mvp-task-list.md` 将从功能愿望列表调整为版本化执行清单。每个任务至少包含：

- 稳定任务 ID；
- 优先级；
- 前置依赖；
- 明确交付物；
- 可验证验收条件；
- 当前状态。

首轮只详细拆解 MVP 0.1。0.2 及以后保留阶段目标和进入条件，临近执行时再细化，避免维护远期伪精确计划。

状态统一使用：

- `planned`
- `in_progress`
- `blocked`
- `done`

文档中的 `done` 必须能够指向代码、测试输出或发布物，不以主观判断作为完成依据。

## 6. 验收与质量指标

文档将把“稳定可用”“体验可接受”等描述替换为可测量标准。MVP 0.1 至少定义：

- Windows 上完成完整 TXT 阅读闭环；
- UTF-8、UTF-16 和 GB18030 编码检测失败时提供明确错误，不静默产生乱码；
- 50 MB TXT 在目标开发机上的导入耗时和峰值内存有基准记录；
- 阅读进度在正常退出、应用被终止和重新启动后均可恢复；
- 数据库迁移测试、核心领域单元测试和关键页面组件测试通过；
- `flutter analyze` 无错误；
- `flutter test` 全部通过；
- 已知限制记录在发布说明中。

具体性能阈值在完成基线测量后写入 `docs/quality-strategy.md`。在没有测量前，不承诺缺乏依据的绝对数值。

## 7. 数据与同步设计边界

### 7.1 本地数据

`docs/data-model.md` 需要明确：

- 媒体、媒体库条目、内容单元、阅读进度、书签和阅读设置的职责；
- 小说和漫画共用字段与专属字段；
- 文件身份、重复导入和文件移动后的处理；
- 软删除与物理删除；
- 索引、约束和数据库迁移；
- 原始文件、派生数据和缓存的生命周期。

### 7.2 同步

同步不以单纯比较客户端 `updated_at` 作为完整冲突方案。`docs/sync-protocol.md` 必须定义：

- 客户端操作 ID 和幂等；
- 服务端单调版本或同步游标；
- 删除标记传播；
- 全量初始化与增量同步；
- 同一实体的冲突策略；
- 设备时间不可信时的处理；
- 重试、退避、恢复和数据重建；
- 协议版本兼容。

同步文档在 Version 0.4 开始前必须完成评审；它不是 MVP 0.1 的实现前置条件。

## 8. GitHub 与求职展示要求

每个可展示版本除功能外，还需要提供：

- 清楚的项目截图或短演示；
- 架构图和关键取舍说明；
- 可复现的安装与运行步骤；
- 自动化检查结果；
- 已知问题和明确的非目标范围；
- GitHub Release 和变更记录；
- 能够说明一次真实性能、数据一致性或异常恢复问题的工程记录。

展示材料必须来自已经实现并验证的能力，不用尚未落地的技术栈包装项目成熟度。

## 9. 风险与处理

### 范围膨胀

所有新增需求必须先分配到明确版本。不能证明服务当前版本核心演示路径的功能，默认延后。

### 架构过度设计

Go、PostgreSQL、Rust 和在线内容源不得仅为展示技术栈而提前引入。

### 内容与许可证

本地导入是早期默认内容来源。在线漫画源、视频源和下载功能必须先完成内容来源、平台条款、缓存行为和第三方许可证评估。

### 文档失真

README 必须标明当前实现阶段。未完成能力使用“计划”而不是“支持”。每个版本发布时同步检查文档导航、状态和已知限制。

## 10. 本次修改范围

本次实施将：

1. 重写根 `README.md` 的状态、路线和导航。
2. 重构 `plan.md`，统一版本范围和优先级。
3. 重构 `docs/mvp-task-list.md`，详细拆解 MVP 0.1。
4. 收敛 `docs/tech-architecture.md` 和 `docs/project-structure.md` 的重复内容。
5. 更新 `docs/dev-setup.md`，移除容易过期且无日期的断言。
6. 更新 `docs/README.md` 的文档索引与维护规则。
7. 新增数据模型、小说、漫画、同步、质量、发布和 ADR 文档。

本次实施不修改 Flutter、Go 或 Rust 代码，不安装依赖，不创建发布包。

## 11. 完成标准

文档重构完成时必须满足：

- 所有文档对 MVP 0.1、0.2、0.3、0.4 的范围表述一致；
- 早期平台统一为 Windows，0.2 增加 Android；
- 下载、番剧、在线内容源和 Rust 不再出现在早期 MVP 必做项；
- 总计划的执行顺序统一为工程骨架、本地数据、小说、漫画、同步；
- 文档导航不存在已创建文件仍被列为“待新增”的情况；
- 关键验收条件可通过命令、测试、基准或演示路径验证；
- Markdown 链接指向存在的仓库文件；
- 不使用 `TBD`、`TODO` 或未解释的占位内容。
