# mirascope 质量策略

## 1. 原则

- 质量结论必须有当次命令、测试或基准记录；
- 当前只为已经承诺的平台设置发布门槛；
- 核心数据和恢复行为优先于页面数量；
- 性能先建立基线，再冻结阈值；
- 手工验证不能替代适合自动化的领域规则。

## 2. 测试层级

| 层级 | 重点 | MVP 0.1 示例 |
|---|---|---|
| 单元测试 | 纯规则和状态转换 | 编码、章节、指纹、进度 revision |
| 数据层集成测试 | 数据库、事务、迁移、文件协调 | 导入回滚、空库与旧版升级 |
| Widget 测试 | 页面状态与关键交互 | 媒体库、目录、阅读设置 |
| 端到端手工验证 | 真实平台与文件系统 | Windows 核心演示路径 |
| 构建检查 | 发布产物可生成 | Windows release 构建 |

MVP 0.2 增加 Android 构建、实机主流程和平台存储权限检查。Version 0.3 增加图片解码、缓存和大章节场景；Version 0.4 增加 API、数据库和同步故障测试。

## 3. MVP 0.1 合并门槛

每次准备合并到主分支前运行：

```bash
dart format --output=none --set-exit-if-changed lib test
flutter analyze
flutter test
flutter build windows
```

要求：

- 格式检查退出码为 0；
- Analyze 无 error；
- 测试 0 failure；
- Windows 构建退出码为 0；
- 新增或改变领域规则时包含对应测试；
- 失败的检查不得以“与本次无关”直接忽略，必须记录原因并修复或获得明确豁免。

GitHub Actions 在推送、面向 `main` 的 Pull Request 和手工触发时执行同等门槛。自动 Windows 构建只证明产物能够生成，不替代真实文件系统和窗口交互的人工验收。

## 4. 发布门槛

除合并门槛外：

- 从干净检出按 `docs/dev-setup.md` 完成依赖获取和构建；
- 执行当前版本全部核心演示路径；
- 验证上一发布数据库升级；
- 验证正常关闭与异常终止后的进度恢复；
- 检查安装说明、截图、版本号和已知问题；
- 按 `docs/release-checklist.md` 留下证据。

## 5. 性能基准

### 5.1 记录格式

每次基准记录：

```text
日期
Git commit
操作系统和版本
CPU、内存
Flutter/Dart 版本
构建模式
样本名称、格式、大小、章节或图片数
预热次数和正式运行次数
每次结果、中位数、峰值内存
```

### 5.2 小说基准

至少包含小型、常规和 50 MB TXT，记录导入、打开、章节切换和峰值内存。每组至少正式运行三次，以中位数作为比较值。

### 5.3 阈值冻结

第一次实现只建立基线。经过真实使用确认后，在同一测试环境冻结具体阈值和允许回归比例。未完成基线时不能宣称“性能达标”。

## 6. 测试数据

- 自建或许可明确的样例文件；
- 编码、章节、空文件、损坏文件和大文件分别保存；
- 不提交受版权保护的完整商业内容；
- 敏感路径、用户名和 Token 不进入快照或日志；
- 大型基准文件若不适合进入 Git，提供可验证的生成脚本或哈希和来源说明。

## 7. 缺陷等级

- **阻塞**：数据丢失、安全问题、核心路径不可用、应用无法启动；
- **严重**：主要功能错误且没有合理绕行；
- **一般**：局部错误，有明确绕行；
- **轻微**：视觉或文案问题，不影响任务完成。

阻塞缺陷禁止发布。严重缺陷默认阻止发布，除非明确缩减版本范围并在已知问题中说明。

## 8. 证据保存

Pull Request 或版本记录至少包含执行命令、结果摘要、手工验证平台和异常。不得复制旧版本结果冒充本次验证。
